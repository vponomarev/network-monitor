# TASK-05 — (C-3) Асинхронное обогащение имени процесса (кэш PID→comm с TTL)

**Метка исполнителя:** 🧠 strong (🐧 linux-host для проверки)
**Зависит от:** TASK-04 желательно (чистый цикл чтения)
**Оценка:** ~1 день

---

## Контекст (проблема)

`internal/conntrack/tracker_linux.go:461, 499-540` — в hot-path на **каждое
событие** синхронно читается `/proc/<pid>/comm` (`enrichProcessName` →
`getProcessComm`). При высоком churn соединений это добавляет задержку в
потребителе ringbuf и провоцирует дропы событий.

Заметка: eBPF-программа уже кладёт `comm[16]` в событие (`bpf_get_current_comm`),
и `enrichProcessName` вызывает `/proc` только когда eBPF-comm пуст. Но даже этот
fallback синхронный в hot-path.

## Что сделать

1. Ввести **кэш PID→comm с TTL** (например, `map[uint32]commEntry` под `sync.RWMutex`
   или `sync.Map`, где `commEntry{name string; expires time.Time}`; TTL ~30–60s).
2. В hot-path:
   - если eBPF-comm непустой — использовать его как сейчас (быстрый путь, без /proc);
   - если пустой — взять из кэша; при промахе кэша **не** блокировать hot-path
     синхронным чтением `/proc`, а поставить PID в очередь на асинхронное
     обогащение (буферизованный канал) и временно отдать `"unknown"`/пусто.
3. Отдельная **горутина-обогатитель** читает `/proc/<pid>/comm`, кладёт в кэш;
   последующие события с тем же PID получают имя из кэша. Корректно завершается
   по `ctx.Done()`.
4. Очередь обогащения — с ограниченным буфером и дедупликацией PID (не плодить
   чтения одного PID); при переполнении — просто пропускать (best-effort).
5. Периодически чистить протухшие записи (или ленивая инвалидция по `expires`).

## Критерии приёмки (DoD)
1. В hot-path нет синхронного `os.ReadFile("/proc/...")` (убедиться грепом, что
   `getProcessComm` вызывается только из горутины-обогатителя).
2. Повторные события одного PID берут comm из кэша (нет повторных чтений /proc).
3. Кэш имеет TTL и очистку; горутина завершается по контексту.
4. Существующие тесты `enrichProcessName`/`getProcessComm` адаптированы/зелёные.
5. `go build ./... && go test ./... && gofmt -l .` — чисто.

## Как проверить
```bash
go test -run 'enrichProcessName|getProcessComm|comm' ./internal/conntrack/...
# нагрузочно (опц.): много короткоживущих соединений — убедиться, что дропы
# (droppedEvents / метрика из TASK-06) не растут из-за /proc.
```

## Риски
- Гонки: кэш и очередь — под корректной синхронизацией; прогнать `go test -race`.
- Не терять корректность: если процесс уже умер, `/proc/<pid>/comm` недоступен —
  оставлять `"unknown"`, не падать (текущая логика уже это учитывает).
- TTL и размер очереди сделать конфигурируемыми константами с разумными дефолтами.
